# GPTHUB

Самохостящаяся AI-платформа на базе [Open WebUI](https://github.com/open-webui/open-webui) с собственным пайплайном, базой данных и полноценным стеком мониторинга (Prometheus + Grafana + cAdvisor). Проект развёрнут на одном VPS и служит полигоном для практики DevOps: контейнеризация, мониторинг, нагрузочное тестирование.

## Архитектура

| Сервис | Назначение | Порт на хосте |
|---|---|---|
| Open WebUI | веб-интерфейс чата | 3000 |
| Pipelines (`pipelines_logic/`) | собственная логика обработки запросов, интеграция с MWS API | 9099 |
| PostgreSQL | база данных Open WebUI | только внутри сети Docker |
| Prometheus | сбор метрик | только внутри сети Docker |
| cAdvisor | метрики контейнеров | только внутри сети Docker |
| Grafana | дашборды | 3001 |

Конфигурация всех сервисов описана в `docker-compose.yml`, сбор метрик в `prometheus.yml`.

## Структура репозитория

```
.
├── docker-compose.yml     # описание стека
├── prometheus.yml         # цели сбора метрик
├── pipelines_logic/       # код пайплайнов
├── k6/                    # сценарии нагрузочного тестирования
├── .env.example           # шаблон переменных окружения (без значений)
└── README.md
```

Данные (`postgres_data/`, тома Prometheus и Grafana) и файл `.env` в репозиторий не попадают, они перечислены в `.gitignore`.

## Быстрый старт

```bash
git clone git@github.com:Dars1k23/GPTHUB.git
cd GPTHUB
cp .env.example .env        # заполните значения
docker compose up -d
docker compose ps           # все сервисы должны быть Up / healthy
```

После запуска:
- Open WebUI: `http://<адрес-сервера>:3000`
- Grafana: `http://<адрес-сервера>:3001`

### Переменные окружения

| Переменная | Для чего |
|---|---|
| `POSTGRES_PASSWORD` | пароль базы данных |
| `WEBUI_SECRET_KEY` | секрет для подписи сессий Open WebUI (генерируйте `openssl rand -hex 32`) |
| `OPENAI_API_KEY` | ключ OpenAI-совместимого API (OpenRouter) |
| `MWS_API_KEY` | ключ MWS API для пайплайна |
| `PIPELINES_API_KEY` | ключ доступа к Pipelines |
| `GF_SECURITY_ADMIN_PASSWORD` | пароль администратора Grafana |

Пароль базы нельзя менять только правкой `.env`: в уже инициализированной базе он останется прежним. Смену делайте через `ALTER USER` внутри контейнера.

## Мониторинг

Prometheus собирает метрики контейнеров из cAdvisor, Grafana рисует их по источнику данных `http://prometheus:9090`.

Панели дашборда:
- **CPU**: загрузка процессора по контейнерам и по хосту целиком;
- **Память**: потребление по контейнерам, красная линия на пределе физической памяти;
- **Сеть** и **диск**: входящий и исходящий трафик, чтение и запись;
- **Прогноз памяти**: линейная экстраполяция на 4 часа вперёд (для поиска утечек при длительных тестах);
- **Скорость роста памяти**: производная по окну 30 минут.

Основные запросы:

```promql
# CPU хоста, %
sum(rate(container_cpu_usage_seconds_total{id="/"}[2m])) / machine_cpu_cores * 100

# Память контейнеров
container_memory_working_set_bytes{id=~"/system.slice/docker-.*"}

# Прогноз памяти через 4 часа
predict_linear(container_memory_working_set_bytes{id=~"/system.slice/docker-.*"}[1h], 4*3600)
```

Мониторинг работает на том же сервере, что и приложение, поэтому под перегрузкой сам начинает тормозить. Для боевой эксплуатации его стоит вынести на отдельную машину.

## Нагрузочное тестирование

Инструмент: [k6](https://k6.io). Тесты запускались с рабочей машины через VPN-сеть (Tailscale) на сервер с 1 vCPU и 1,92 ГБ RAM. Нагружалась главная страница Open WebUI, чат-эндпоинты не использовались, чтобы не расходовать платные API-ключи.

```bash
k6 run -e BASE_URL=http://<адрес-сервера>:3000 k6/smoke.js
```

Во время прогона мониторинг и `htop` на сервере открыты параллельно.

### Результаты

| Тест | Профиль | Запросов | Ошибки | p(95) | Запросов/с |
|---|---|---|---|---|---|
| Smoke, `/health` | до 50 VU, 2 мин, пауза 1 с | 2 505 | 0% | 94 мс | ~21 |
| Load, главная | до 500 VU, 6 мин, пауза 0,5 с | 70 148 | 0% | 1,75 с | ~195 |
| Stress, главная | до 1000 VU, 6 мин, пауза 0,5 с | 60 359 | 1,64% | 6,55 с | ~167 |
| Spike, главная | скачок до 1000 VU, 3,5 мин | 43 521 | 0,44% | 3,3 с | ~207 |

Soak-тест (постоянная нагрузка порядка 120 запросов/с в течение нескольких часов) запланирован.

### Выводы

- **Предел пропускной способности около 200 запросов/с** на главную страницу. При удвоении числа пользователей (500 → 1000) пропускная способность не выросла (195 → 167), то есть сервер вошёл в насыщение и лишние запросы только растят очередь.
- **Узкое место: единственное ядро процессора.** На пике `htop` показывал 100%: около половины занимал Open WebUI, около 15% шифрование туннеля Tailscale, около 15% фоновые процессы snapd. Памяти на пике занято 1,39 из 1,92 ГБ, OOM-убийств не было.
- **Деградация плавная, без падений.** Контейнеры не перезапускались, после спада нагрузки процессор и сеть вернулись к фоновому уровню.
- **Ограничения методики.** Нагрузка шла через туннель, поэтому в задержку входит около 65–90 мс сетевой составляющей, а часть ядра сервера тратится на шифрование. Модель закрытая (фиксированное число VU с паузой): для чистого поиска предела надёжнее открытая модель с заданным темпом запросов.

## Безопасность

- Секреты хранятся только в `.env` (в репозитории только `.env.example`).
- Порты 3000, 3001 и 9099 желательно не публиковать в интернет: привяжите их к адресу VPN-интерфейса или к `127.0.0.1` и ходите через Tailscale.
- Ключи внешних API периодически перевыпускайте, пароли по умолчанию (`admin`, `0000`) замените на случайные значения.
